# Migrate from Pigeon

Guide to migrating from Pigeon to native_bridge_kit. Learn the differences and how to convert your existing Pigeon setup.

## Architecture Differences

### Pigeon Approach

```
Pigeon AST Definition (.dart)
         ↓
Generated Dart Code (pigeon_model.g.dart)
         ↓
Generated Kotlin & Swift
```

### native_bridge_kit Approach

```
Dart Contract (@NativeBridge) ← Single source of truth
         ↓
Generated Dart Code (my_bridge.g.dart)
         ↓
Generated Kotlin & Swift Stubs
```

**Key Difference**: native_bridge_kit uses your Dart contract as-is; Pigeon requires a separate API definition.

## Feature Comparison

| Feature | Pigeon | native_bridge_kit |
|---------|--------|---------------|
| Dart-First | ✓ Yes | ✓ Yes |
| Type Safety | ✓ Full | ✓ Full |
| Future Support | ✓ Yes | ✓ Yes |
| Stream Support | ✓ Yes | ✓ Yes |
| Unit Testing | ✗ Integration only | ✓ MockBridgeTransport |
| Contract Sync Check | ✗ Manual | ✓ drift-check CLI |
| Custom Types | ✓ Limited | ✓ Flexible mapping |
| Learning Curve | Medium | Low |
| Boilerplate | Medium | Low |

## Migration Steps

### Step 1: Analyze Current Pigeon Setup

**Current Pigeon structure:**

```
pigeon/
├── messages.dart        # Pigeon API definition
└── pigeons/
    ├── android/
    └── ios/
```

**Pigeon example:**

```dart
// pigeon/messages.dart
import 'package:pigeon/pigeon_flutter.dart';

class DeviceMessage {
  String? model;
  int? batteryLevel;
}

@FlutterApi()
abstract class FlutterDeviceApi {
  void onBatteryChanged(int level);
}

@HostApi()
abstract class HostDeviceApi {
  Future<DeviceMessage> getDeviceInfo();
}
```

### Step 2: Add native_bridge_kit

Add to `pubspec.yaml`:

```yaml
dependencies:
  native_bridge_kit_annotation: ^0.1.0
  native_bridge_kit: ^0.1.0

dev_dependencies:
  build_runner: ^2.4.0
  native_bridge_kit_gen: ^0.1.0
  native_bridge_kit_android_gen: ^0.1.0
  native_bridge_kit_ios_gen: ^0.1.0
```

```bash
flutter pub get
```

### Step 3: Convert Pigeon API to native_bridge_kit Contract

**OLD (Pigeon):**

```dart
// pigeon/messages.dart
class DeviceMessage {
  String? model;
  int? batteryLevel;
}

@HostApi()
abstract class HostDeviceApi {
  Future<DeviceMessage> getDeviceInfo();
}
```

**NEW (native_bridge_kit):**

```dart
// lib/native/device_bridge.dart
import 'package:native_bridge_kit_annotation/native_bridge_kit_annotation.dart';

part 'device_bridge.g.dart';

@NativeBridge()
abstract class DeviceBridge {
  Future<Map<String, dynamic>> getDeviceInfo();
}
```

### Step 4: Generate Code

```bash
flutter pub run build_runner build
```

Creates:
- `lib/native/device_bridge.g.dart` — Dart implementation
- `DeviceBridgeHandler.g.kt` — Android Kotlin stubs
- `DeviceBridgeHandler.g.swift` — iOS Swift stubs

### Step 5: Update Android Handler

**OLD (Pigeon):**

```kotlin
// pigeon/android/HostDeviceApi.kt
// Generated by Pigeon - do not edit

class HostDeviceApi {
  fun getDeviceInfo(): DeviceMessage {
    // Implemented in MainActivity
  }
}
```

**NEW (native_bridge_kit):**

```kotlin
// android/app/src/main/kotlin/com/example/app/DeviceBridgeHandler.kt
class DeviceBridgeHandler(private val context: Context) {
  fun getDeviceInfo(): Map<String, Any> {
    // BEGIN_USER_CODE
    return mapOf(
      "model" to Build.MODEL,
      "batteryLevel" to 75,
    )
    // END_USER_CODE
  }
}
```

### Step 6: Update iOS Handler

**OLD (Pigeon):**

```swift
// pigeon/ios/HostDeviceApi.swift
// Generated by Pigeon - do not edit

protocol HostDeviceApi {
  func getDeviceInfo(_ completion: (DeviceMessage) -> Void)
}
```

**NEW (native_bridge_kit):**

```swift
// ios/Runner/DeviceBridgeHandler.swift
class DeviceBridgeHandler {
  func getDeviceInfo() -> [String: Any] {
    // MARK: - BEGIN USER CODE
    return [
      "model": UIDevice.current.model,
      "batteryLevel": 75,
    ]
    // MARK: - END USER CODE
  }
}
```

### Step 7: Update Dart Usage

**OLD (Pigeon):**

```dart
import 'pigeon/messages.dart';

final api = HostDeviceApi();
final info = await api.getDeviceInfo();
print(info.model);
print(info.batteryLevel);
```

**NEW (native_bridge_kit):**

```dart
import 'package:my_app/native/device_bridge.g.dart';

final bridge = DeviceBridgeImpl(MethodChannelTransport());
final info = await bridge.getDeviceInfo();
print(info['model']);
print(info['batteryLevel']);
```

### Step 8: Add Unit Tests

No need for platform-specific testing:

```dart
test('get device info', () async {
  final transport = MockBridgeTransport();
  transport.stubMethodValue('getDeviceInfo', {
    'model': 'Pixel 6',
    'batteryLevel': 75,
  });

  final bridge = DeviceBridgeImpl(transport);
  final info = await bridge.getDeviceInfo();

  expect(info['model'], 'Pixel 6');
  expect(info['batteryLevel'], 75);
});
```

```bash
flutter test  # Works! No device needed
```

### Step 9: Remove Pigeon

```bash
# Delete Pigeon directory
rm -rf pigeon/

# Update pubspec.yaml - remove pigeon
# Run build_runner to verify
flutter pub run build_runner build
```

## Trade-offs

### Advantages of native_bridge_kit

1. ✅ **Simpler contract** — Your Dart code IS the API
2. ✅ **Unit testing** — MockBridgeTransport for pure Dart tests
3. ✅ **Type mapping** — Easy custom type conversions
4. ✅ **drift-check** — Automated sync validation
5. ✅ **Less boilerplate** — Generated code handles more

### Advantages of Pigeon

1. ✓ **More established** — Mature, battle-tested
2. ✓ **Larger community** — More examples and plugins
3. ✓ **IDE support** — Better autocomplete in some IDEs

## Common Gotchas

### 1. Serialization Differences

Pigeon used custom classes; native_bridge_kit uses Maps:

```dart
// Pigeon
final info = await api.getDeviceInfo();
print(info.model);  // Property access

// native_bridge_kit
final info = await bridge.getDeviceInfo();
print(info['model']);  // Map access
```

### 2. Stream Handling

Pigeon required callbacks; native_bridge_kit uses Streams:

```dart
// Pigeon
api.onBatteryChanged = (level) => print(level);

// native_bridge_kit
bridge.batteryUpdates.listen((level) => print(level));
```

### 3. Error Handling

Different error structures:

```dart
// Pigeon - custom error class
try {
  await api.getDeviceInfo();
} catch (e) {
  // PlatformException or custom error
}

// native_bridge_kit - PlatformException
try {
  await bridge.getDeviceInfo();
} catch (e) {
  if (e is PlatformException) {
    print(e.code);
    print(e.message);
  }
}
```

## Gradual Migration

You can run both side-by-side during migration:

```dart
class DeviceService {
  late final HostDeviceApi _pigeon;  // OLD
  late final DeviceBridge _bridge;   // NEW

  Future<void> init() async {
    _pigeon = HostDeviceApi();
    _bridge = DeviceBridgeImpl(MethodChannelTransport());
  }

  // NEW: Use native_bridge_kit
  Future<Map<String, dynamic>> getDeviceInfoNew() =>
      _bridge.getDeviceInfo();

  // OLD: Use Pigeon (can deprecate later)
  Future<DeviceMessage> getDeviceInfoOld() =>
      _pigeon.getDeviceInfo();
}
```

## Performance Considerations

Both have similar performance. native_bridge_kit has:
- ✓ Slightly less reflection
- ✓ Direct method dispatch
- ✓ Minimal serialization overhead

For most apps, performance difference is negligible.
